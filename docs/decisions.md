# Журнал решений

## Допрос требований — 2026-10-23

### 1. Когда задача считается активной

- **Вопрос:** когда задача перестаёт занимать один из трёх активных слотов пользователя?
- **Решение:** задача активна до перехода в `completed` или `failed`, включая ожидание провайдера, повторные попытки и обработку таймаута.
- **Альтернативы:** освобождать слот после первой отправки провайдеру; определить другой момент завершения активности.
- **Риски:** длительная обработка или зависшая задача дольше занимает слот; сторож должен надёжно доводить просроченные задачи до следующей попытки или терминального состояния.

### 2. Статус вебхука оплаты

- **Вопрос:** как трактовать поле `status` в вебхуке оплаты?
- **Решение:** начислять токены только при `status: "succeeded"`; остальные статусы подтверждать без изменения баланса.
- **Альтернативы:** отклонять все неуспешные статусы как некорректные запросы; сохранять и обрабатывать полный жизненный цикл статусов оплаты.
- **Риски:** контракт провайдера должен использовать ровно `succeeded`; другое значение успешного статуса не приведёт к начислению.

### 3. Возврат токенов при ошибке `payload`

- **Вопрос:** возвращать ли токены, если провайдер отклонил задачу с ошибкой `payload`?
- **Решение:** ошибка `payload` немедленно завершает задачу и приводит к однократному возврату токенов. Если некорректность запроса обнаруживается до списания, API отвечает `400` без списания.
- **Альтернативы:** не возвращать токены после принятия задачи; различать ошибку, найденную API, и ошибку, сообщённую провайдером, при этом возвращая токены только во втором случае.
- **Риски:** повторная реализация возврата в разных путях может нарушить гарантию однократности; возврат должен быть атомарен с записью в журнал.

### 4. Формат `ref_images`

- **Вопрос:** в каком формате API принимает элементы `ref_images`?
- **Решение:** принимать массив HTTP(S)-ссылок и проверять формат до списания токенов.
- **Альтернативы:** принимать непрозрачные строки; передавать изображения в base64.
- **Риски:** ссылка может истечь или стать недоступной после приёма запроса; сервис не хранит копию изображения.

### 5. Повторный вебхук с конфликтующими данными

- **Вопрос:** что делать, если вебхук с уже известным `payment_id` содержит другой `user_id` или `tokens`?
- **Решение:** первый успешный вебхук фиксирует данные платежа; точный повтор подтверждается без повторного начисления, конфликтующий повтор отклоняется без изменения баланса.
- **Альтернативы:** молча подтверждать любой повтор с тем же `payment_id`; применять последние полученные данные.
- **Риски:** первый принятый набор данных становится авторитетным; исправление ошибочных реквизитов платежа потребует отдельного процесса корректировки.

### 6. Оплата для неизвестного пользователя

- **Вопрос:** что делать с успешной оплатой для `user_id`, которого ещё нет в базе?
- **Решение:** создать пользователя с нулевым балансом и начислить токены через журнал операций.
- **Альтернативы:** отклонять оплату и требовать предварительного создания пользователя внешней системой; создавать пользователя при первом `POST /generate`.
- **Риски:** валидный подписанный вебхук становится путём создания пользователя; корректность зависит от проверки подписи до создания записи и начисления.

### 7. Строковое значение успешного статуса оплаты

- **Вопрос:** какое значение `status` означает успешную оплату?
- **Решение:** использовать ровно `succeeded`; остальные статусы не начисляют токены.
- **Альтернативы:** использовать `paid`; принимать оба значения.
- **Риски:** провайдер с другим написанием статуса потребует явного изменения контракта.

### 8. Неизвестная модель в запросе генерации

- **Вопрос:** какой ответ возвращать на `POST /generate` с неизвестным `model_slug`?
- **Решение:** вернуть `404` до списания токенов и создания задачи.
- **Альтернативы:** вернуть `400` как ошибку параметра; создать задачу и завершить её позднее.
- **Риски:** клиент должен различать отсутствие модели (`404`) и некорректную форму запроса (`400`).

### 9. Неизвестный пользователь в запросе генерации

- **Вопрос:** что возвращать на `POST /generate` для отсутствующего `user_id`?
- **Решение:** вернуть `404`, не создавая пользователя и задачу.
- **Альтернативы:** вернуть `402`, трактуя пользователя как имеющего нулевой баланс; создать пользователя с нулевым балансом и вернуть `402`.
- **Риски:** клиент должен отличать неизвестного пользователя (`404`) от известного пользователя с недостаточным балансом (`402`).

### 10. Переход статуса платежа

- **Вопрос:** может ли статус одного платежа измениться с промежуточного или неуспешного на успешный?
- **Решение:** да; неуспешные и промежуточные события не блокируют позднейшее событие `succeeded` с тем же `payment_id`. Платёж считается обработанным для идемпотентности при успешном начислении.
- **Альтернативы:** считать каждый вебхук итоговым статусом; хранить и обрабатывать полный переход статусов платежа.
- **Риски:** промежуточные/неуспешные события не сохраняют состояние платежа; успешный callback должен быть самодостаточным и содержать окончательные `user_id` и `tokens`.

### 11. Необязательное поле `ref_images`

- **Вопрос:** обязательно ли передавать `ref_images`, если референсов нет?
- **Решение:** поле можно опустить; отсутствие трактуется как пустой список. `null` и значения не-массивы отклоняются с `400`.
- **Альтернативы:** требовать явный пустой список; трактовать и отсутствие, и `null` как пустой список.
- **Риски:** клиентам нужно различать пропущенное поле и явный `null`; это поддерживает строгую форму запроса.

### 12. Пустой prompt

- **Вопрос:** можно ли отправить пустой или состоящий из пробелов `prompt`?
- **Решение:** требовать непустую строку после удаления пробелов; иначе вернуть `400` до списания токенов.
- **Альтернативы:** передавать пустой prompt провайдеру и полагаться на его `payload`-отказ; проверять только длину строки без учёта пробелов.
- **Риски:** нормализация пробелов должна быть одинаковой во всех запросах и тестах; пробелы по краям не являются частью сохранённого prompt только если реализация отдельно решит их обрезать.

### 13. Значение `tokens` в вебхуке оплаты

- **Вопрос:** какие значения допустимы в поле `tokens`?
- **Решение:** принимать только положительное целое число; нулевые, отрицательные и дробные значения отклонять без начисления.
- **Альтернативы:** разрешить ноль как пустую операцию; трактовать отрицательное значение как списание или возврат.
- **Риски:** большие положительные значения требуют безопасного диапазона хранения; формат API должен отвергать дробные значения, а не округлять их.

### 14. Ссылка на результат задачи

- **Вопрос:** должен ли `GET /tasks/{id}` возвращать ссылку на результат генерации?
- **Решение:** возвращать `result_url` для завершённой задачи и `null` для остальных состояний.
- **Альтернативы:** не включать ссылку в GET-ответ; добавить отдельный endpoint для результата.
- **Риски:** ссылка остаётся внешней строкой и может стать недоступной; сервис не хранит файл.

### 15. Нормализация prompt

- **Вопрос:** изменять ли пробелы по краям `prompt` после проверки, что он не пустой?
- **Решение:** проверять `prompt.strip()` на непустое значение, но сохранять и передавать исходную строку без изменений.
- **Альтернативы:** обрезать пробелы по краям перед сохранением и отправкой; отклонять строки с пробелами по краям.
- **Риски:** строки с одинаковым содержимым и разным числом пробелов по краям остаются различными для провайдера.

### 16. Размер истории баланса

- **Вопрос:** сколько строк журнала возвращать из `GET /users/{id}/balance`?
- **Решение:** возвращать 20 последних строк журнала в порядке от новых к старым.
- **Альтернативы:** возвращать весь журнал; добавить пагинацию.
- **Риски:** фиксированный лимит не позволяет просмотреть более старые строки через этот endpoint.

### 17. Баланс неизвестного пользователя

- **Вопрос:** что возвращать из `GET /users/{id}/balance`, если пользователя нет?
- **Решение:** вернуть `404`, не создавая пользователя.
- **Альтернативы:** вернуть `200` с нулевым балансом и пустым журналом; создать пользователя при чтении.
- **Риски:** клиенту нужно обрабатывать отсутствие пользователя отдельно от нулевого баланса.

### 18. Неизвестная задача

- **Вопрос:** что возвращать из `GET /tasks/{id}`, если задачи с таким ID нет?
- **Решение:** вернуть `404`.
- **Альтернативы:** вернуть `200` с состоянием `not_found`; трактовать неизвестный ID как `400`.
- **Риски:** клиент должен трактовать `404` отдельно от терминального состояния `failed`.

### 19. Неверная подпись вебхука

- **Вопрос:** что делать с вебхуком без подписи или с неверной HMAC-подписью?
- **Решение:** вернуть `401` и не менять состояние задачи или баланс.
- **Альтернативы:** вернуть `403`; принимать неподписанные вебхуки в тестовом режиме.
- **Риски:** отправитель должен получить корректный общий секрет и формат подписи; неверная конфигурация остановит все callback-запросы.

### 20. Представление HMAC в заголовке

- **Вопрос:** в каком текстовом формате передавать HMAC-SHA256 в `X-Signature`?
- **Решение:** lowercase hex digest без префикса.
- **Альтернативы:** префикс `sha256=` перед hex; Base64 от digest.
- **Риски:** провайдеры должны в точности использовать выбранное кодирование и регистр.

### 21. Содержимое истории попыток

- **Вопрос:** какие обращения к провайдерам включать в историю попыток?
- **Решение:** включать каждую попытку отправки, в том числе синхронный `503` или таймаут до `202`, а также ошибки, пришедшие вебхуком. У успешной попытки тип ошибки отсутствует.
- **Альтернативы:** включать только принятые провайдером запросы; показывать только неудачные попытки.
- **Риски:** записи попыток должны различать синхронный отказ и асинхронную ошибку, иначе историю можно неверно интерпретировать.

### 22. Статусы задачи

- **Вопрос:** какие значения статуса задачи показывать через `GET /tasks/{id}`?
- **Решение:** использовать `processing`, `completed`, `failed`; задача имеет `processing` с момента создания до терминального состояния.
- **Альтернативы:** добавлять `queued` до первого принятого провайдером запроса; отражать непосредственно статусы провайдеров.
- **Риски:** клиенты не различают ожидание отправки и ожидание результата; это приемлемо для простого контракта с одним статусом процесса.

### 23. `current_leg` в терминальном состоянии

- **Вопрос:** что показывать в `current_leg`, когда задача уже завершена или упала?
- **Решение:** сохранять последнюю выбранную ногу и возвращать её даже в терминальном состоянии.
- **Альтернативы:** возвращать `null` после завершения; показывать следующую ногу, даже если задача на неё не отправлялась.
- **Риски:** поле `current_leg` после терминального состояния означает последнюю ногу, а не активную; это нужно явно описать в API/README.

### 24. Порядок истории попыток

- **Вопрос:** в каком порядке возвращать историю попыток задачи?
- **Решение:** от первой попытки к последней, по возрастанию времени.
- **Альтернативы:** новые попытки первыми; не гарантировать порядок и перекладывать сортировку на клиента.
- **Риски:** при одинаковом времени создания записей нужен стабильный дополнительный порядок, например номер попытки.

### 25. Код ответа при создании задачи

- **Вопрос:** какой HTTP-код возвращать при успешном `POST /generate`?
- **Решение:** `202 Accepted`, так как генерация выполняется асинхронно.
- **Альтернативы:** `201 Created` для созданного ресурса; `200 OK` как общий успешный ответ.
- **Риски:** клиент трактует ответ как принятие задачи, а не как завершённую генерацию.

## Итог допроса — 2026-10-23

### Принятые решения

1. Задача занимает слот до `completed` или `failed`, включая ожидание, повторы и обработку таймаута.
2. Баланс пополняется только для `status: "succeeded"`; другие статусы не меняют баланс, а поздний `succeeded` с тем же `payment_id` допустим.
3. Платёжный вебхук требует положительное целое `tokens`. Успешная оплата неизвестного пользователя создаёт его и журналирует начисление.
4. Идемпотентность платежа определяется `payment_id`: точный повтор не начисляет снова, несовпадающие `user_id`/`tokens` дают конфликт; промежуточный статус не занимает ключ.
5. Ошибка провайдера `payload` завершает задачу и возвращает токены ровно один раз. Ошибка запроса, выявленная до списания, даёт `400` без списания.
6. `ref_images` — необязательный массив HTTP(S)-ссылок: отсутствие равно `[]`, `null` или неверный тип — `400`; формат проверяется до списания.
7. `prompt` должен быть непустым после `strip()`, но исходное значение сохраняется без обрезки.
8. Неизвестные модель, пользователь или задача дают `404`; запрос генерации известного пользователя с недостаточным балансом — `402`; неизвестный пользователь не создаётся при чтении или генерации.
9. `GET /tasks/{id}` возвращает ссылку `result_url` после завершения; статусы задачи — `processing`, `completed`, `failed`; `current_leg` остаётся последней выбранной ногой и в терминальном состоянии.
10. История попыток включает все отправки и ошибки, в том числе синхронные; порядок — от первой попытки к последней. Баланс возвращает 20 последних строк журнала от новых к старым.
11. HMAC считается по сырому телу; `X-Signature` — lowercase hex без префикса. Отсутствующая или неверная подпись даёт `401` без изменений состояния.
12. Успешный `POST /generate` возвращает `202 Accepted`.
13. `completed` после таймаута попытки не меняет задачу или баланс: попытка помечается `late_ignored`, вебхук подтверждается `200`.

### Допущения по умолчанию

1. **Все ноги синхронно отклонили отправку:** всё равно вернуть `202` с `task_id`; завершить задачу как `failed` и вернуть токены. Обоснование: запрос породил сохранённую задачу и её итог доступен через указанный API.
2. **Повторные/терминальные callback:** корректно подписанный дубликат или callback для уже терминальной задачи получает `200` без повторного изменения состояния/баланса; поздний `completed` для попытки, уже просроченной сторожем, фиксируется как `late_ignored`. Обоснование: подтверждение доставки не должно повторно запускать обработку.
3. **Неизвестный provider path / некорректное тело:** `404` / `400`, без побочных эффектов. Обоснование: это неизвестный endpoint или невалидный запрос.
4. **Доступность URL-референсов:** проверять только абсолютный HTTP(S)-формат, не обращаться по ссылкам и не скачивать файлы. Обоснование: для валидации формы не нужна внешняя сеть, а хранение файлов исключено заданием.
5. **Максимальная длина `prompt`:** отдельный бизнес-лимит не вводить. Обоснование: задание ограничивает только пустое значение и не задаёт максимум.
6. **Срок хранения обработанного `payment_id`:** бессрочно. Обоснование: повторное начисление после удаления ключа нарушило бы требование «ровно один раз».

### 26. Поздний `completed` и гонка со сторожем/возвратом

- **Вопрос:** как обрабатывать `completed`, пришедший после таймаута сторожа?
- **Решение:** терминальное решение сторожа по попытке побеждает. Поздний `completed` фиксируется в истории попытки как `late_ignored`, получает HTTP `200` и не меняет статус задачи, результат или баланс.
- **Альтернативы:** принимать поздний результат, пока задача ещё `processing`, и останавливать дальнейшие попытки.
- **Компромисс:** работа провайдера может быть выброшена, даже если он успешно завершил генерацию после нашего таймаута.
- **Вариант C — возможное улучшение:** добавить отмену либо сверку удалённой задачи у провайдера после таймаута, если провайдер будет поддерживать такой механизм; в текущем контракте этого нет.
- **Риски:** внешняя работа может продолжаться без использования результата; игнорирование должно быть атомарным относительно статуса попытки, чтобы поздний callback не привёл к возврату и выдаче результата одновременно.

### 27. Тестовый стенд

- **Вопрос:** как проверять поведение сервиса в нескольких процессах и сверять денежное состояние?
- **Решение:** использовать `pytest` + `pytest-asyncio`, `httpx.AsyncClient` против адреса сервиса из Compose и `asyncpg` только для чтения состояния. Тестовые `user_id` и `payment_id` генерируются уникально; данные создаются только через API. `ruff` и `mypy` настроены в единственном `pyproject.toml`.
- **Версии:** FastAPI `0.162.0`, Uvicorn `0.54.0`, pytest `9.1.1`, pytest-asyncio `1.4.0`, HTTPX `0.28.1`, asyncpg `0.32.0`, Ruff `0.17.2`, mypy `2.4.0`, setuptools `84.2.1`; версии проверены по метаданным PyPI 2026-10-23.
- **Альтернативы:** in-process `TestClient` не проходит через четыре worker-процесса; прямые вставки в БД обходят API и не проверяют создание записей реальным запросом.
- **Риски:** тесты требуют запущенного Compose-окружения; SQL helper должен соответствовать именам и типам колонок денежного журнала.
