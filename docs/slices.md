# План вертикальных срезов

Каждый срез проходит через HTTP/API, базу и поведенческий тест. Обязательные тесты из `docs/TASK.md` обозначены номерами 1–4. Общий helper сверки баланса и журнала подключается в первом срезе и запускается после каждого теста.

## Срез 1. Compose и один платёж

- **Что делает:** поднимает PostgreSQL, сервис в четырёх процессах и alpha/beta; применяет первую миграцию с минимальным каталогом; принимает один подписанный успешный payment webhook, создаёт пользователя, начисляет токены и отдаёт баланс с журналом. Добавляет общий helper проверки `balance == sum(ledger)` и начальный скелет README с Compose-командой.
- **Инварианты:** 1, 2, 5.
- **Первый красный тест:** Compose E2E: подписанный `succeeded` для нового пользователя создаёт его, баланс и строку журнала; `GET /users/{id}/balance` возвращает начисление.
- **Граница fake-provider:** оба сервиса только запускаются; сценарии отправки задач пока не добавляются.

## Срез 2. Дубли платежа

- **Что делает:** делает обработку `payment_id` идемпотентной через ограничение БД и транзакцию.
- **Инварианты:** 1, 2, 5.
- **Первый красный тест:** обязательный тест 1 — 20 одновременных одинаковых payment webhook дают одно начисление; проверяется общий helper.
- **Деньги:** закрывает гарантию однократного начисления до добавления списаний и возвратов.

## Срез 3. Приём генерации: `400` и `402`

- Каталог моделей и ног, пропущенный в срезе 1, добавляется в срезе 3.
- **Что делает:** принимает `POST /generate`, проверяет пользователя, модель, prompt, `ref_images` и наличие подходящей ноги; отклоняет неизвестные данные и запрос без подходящей ноги до списания; проверяет достаточный баланс и создаёт задачу со списанием и строкой журнала. Добавляет `CHECK (balance >= 0)` как страховку.
- **Инварианты:** 1, 2, 3, 4.
- **Первый красный тест:** запрос с неподходящими референсами возвращает `400` без изменения баланса/журнала; конкурентные генерации при балансе ровно на одну цену дают один принятый запрос и один `402`.
- **Граница fake-provider:** отправка провайдеру пока не реализуется; поведение этой части начинается в срезе 5.

## Срез 4. Лимит активных задач `429`

- **Что делает:** сериализует приём генераций и проверку лимита; каждая нетерминальная задача занимает один из трёх слотов пользователя.
- **Тест:** 10 параллельных `POST /generate` от пользователя с большим балансом: ровно 3 ответа `202`, 7 ответов `429`, списано ровно три цены.
- **Инварианты:** 1, 3, 4, 6.

## Срез 5. Отправка и `completed`

- **Что делает:** создаёт попытку со статусом `pending`; процесс атомарно захватывает её через `UPDATE ... WHERE status = 'pending' RETURNING` и фиксирует `dispatching` до внешнего HTTP-вызова. При `202` сохраняет внешний ID и статус ожидания. Проверяет подпись вебхука провайдера; `completed` завершает задачу. Фейковый провайдер поддерживает настраиваемую задержку; в тестах — 1–2 секунды.
- **Тест:** один сквозной сценарий от `POST /generate` до подписанного `completed`, с проверкой результата, попытки и текущей ноги.
- **Инварианты:** 1, 2, 3, 7, 8, 9.

## Срез 6. Вторая нога

- **Что делает:** после асинхронного отказа первой ноги создаёт и отправляет следующую попытку, сохраняя порядок истории.
- **Тест:** обязательный тест 3 — первая нога отказывает, задача завершается на второй, в истории две попытки.
- **Инварианты:** 3, 7, 8, 9.

## Срез 7. Исчерпание ног и один возврат

- **Что делает:** завершает задачу после отказа последней ноги и атомарно записывает `failed`, один возврат и строку журнала; применяет правила `moderation` и `payload`.
- **Тесты:** обязательный тест 2 — 10 одновременных `failed` дают один возврат; moderation для `video-long` пропускает ногу с `skip_on_moderation`; `payload` завершает задачу без следующей попытки; синхронный `503` проверяет переход по цепочке.
- **Инварианты:** 1, 2, 3, 7, 8, 9.

## Срез 8. Сторож и поздний `completed`

- **Что делает:** обрабатывает просроченные `dispatching` и `waiting` без двойного перехода в четырёх процессах. `PROVIDER_TIMEOUT` настраивается; в тестах используется короткое значение.
- **Тесты:** обязательный тест 4 — поздний `completed` получает `200`, фиксируется как `late_ignored` и не меняет терминальное состояние/баланс; провайдер молчит, задача переходит на следующую ногу.
- **Инварианты:** 1, 6, 7, 8, 9.

## Срез 9. Финал и README

- **Что делает:** описывает запуск и тесты, миграции, гарантии денег и поведение при падении процесса.
- **Проверка:** чистый клон, `docker compose up`, полный набор тестов; применены миграции с чистой БД, сервис запускается в четырёх процессах.
- **Инварианты:** сквозная проверка инвариантов 1–9.

Дополнительные тесты сверх перечисленных для срезов 4–8 не планировать.
